# 界面与交互优化 + 思考内容不展示修复 —— 需求文档

- 日期：2026-09-13
- 状态：**待确认**（确认后再动手实现）
- 分支：`feat/ui-polish`
- 设计稿：[design.html](design.html)（本轮的界面基线，实现以它为准）
- 实施与验证：[checklist.md](checklist.md)（实现后补）

## 1. 背景

在 v0.1.1 / v0.2.0 上用过几轮后，使用者提出两点：

1. **「目前效果太丑了」**——功能已经齐了，但界面停留在「能用的系统默认样式」：Emoji 当图标、卡片层次靠灰色堆叠、四种列表语法混用（卡片流 / insetGrouped List / Form / 自绘行）、动效稀疏、没有视觉焦点。
2. **「AI 教练对话过程中，reasoning 内容没办法展示」**——第 03 轮做了流式与思考内容，但在真实设备上思考区从来不出现。

第 2 点排查后确认：**这不是显示层的问题，而是流式链路在生产路径上根本没被走到**（根因见 FR11），顺带导致教练回复实际上也不是流式的。两个问题一起在本轮解决。

## 2. 目标

- 建立一套**可复用的视觉语言**（颜色 / 圆角 / 间距 / 字体 / 卡片 / 图标），一次定义、全 App 生效，而不是逐屏微调
- 去掉所有「廉价感」来源：Emoji 图标、嵌套灰卡、开发者文案、无意义的占位
- 让每个页面有**明确的视觉焦点**（今日概览环、课程进度、报告指标），而不是一列等权重的灰卡片
- 交互补上**手感**：数字滚动、插入/删除过渡、触觉反馈、流式渲染不掉帧
- **修复思考内容不展示**，并让教练回复真正逐字流式

### FR13 导航层与列表结构（改为原生写法）

> 原计划做 iOS 26 的浮动玻璃胶囊，实施中发现**结构上不可靠**：浮动胶囊有缝隙和
> 左右边距，背后的内容会透出来；而浮动玻璃的前提是 `backdrop-filter` 生效，
> 一旦模糊不渲染（无 GPU 环境 / 部分浏览器）就直接显形。已改为经典 iOS 写法。

| 项 | 要求 |
|----|------|
| FR13.1 | Tab 栏为**通栏实底** + 顶部 0.5pt 分隔线；**不做浮动胶囊、不依赖 `backdrop-filter`** |
| FR13.2 | 底部输入条为胶囊，位于 Tab 栏之上，背景用 `chip` |
| FR13.3 | 滚动容器底部预留浮层高度，最后一行不被遮挡 |
| FR13.4 | **卡片去掉描边** —— iOS 分组列表靠底色差分层，描边是网页的做法 |
| FR13.5 | **分组标题放在卡片外**（13pt/600/次级色），不放进卡片当第一行 |
| FR13.6 | 行分隔线**内缩 48pt** 与主行文字对齐，不通栏 |

**验收标准**：滚动到底时最后一行完整可见；卡片之间靠底色差可分辨边界，不需要描边；
分组标题在卡片外且与卡片文字左对齐。

**关于「帧率能不能更高」（旧素材的结论，现已不适用）**

> 以下针对 workout-guide 的静态线稿。换用 exercises-dataset 的 12 帧 GIF 后，
> 帧率问题自然消失，本节保留作为选型依据。

使用者反馈「一远一近，帧率能不能高一点」。查下来是三个叠加的问题，
其中两个可修、一个不可修：

| 问题 | 结论 |
|------|------|
| 帧 2 线宽是另两帧的近 2 倍 | 不可修。试过 SVG `feMorphology` 腐蚀（半径离散，1 无效、3 毁图）与阈值削线（线稿是纯白实心、没有渐变可利用）；中帧用不了 |
| 三帧取景未对齐，脚底漂 24–257px | **可修**。逐动作量平移量校正，实测对齐后下缘差为 0 |
| 只有 3 帧，帧率上不去 | **不可修**。素材每个动作就只有 3 帧，没有更多帧可插；且不存在开源的带真动画替代（唯一有的 exercises-dataset 其 GIF 素材版权属 © Gym visual，需另行购买授权） |

**结论**：两帧交替是这批素材的上限。已把取景对齐做掉，剩下的「跳」来自姿态跨度本身 ——
那是动作的真实幅度，不该消除。若要更流畅，只有换付费素材一条路。

**关于「运动方向线」（已否决，附实测依据）**

曾考虑在动图上加一条方向线表示发力方向。逐动作手画需要 60–100 次手工标注且标错即教错，
因此先试了从帧差自动推导：取第 1 与第 3 帧的差分，用变化区域质心的位移方向作为运动方向。

12 个动作实测：**8 个完全推不出**（质心位移低于阈值），**4 个推出来的也是错的** ——
深蹲全过程只有 `10.5px` 位移（画布 256px，占 4.1%），而它的变化区域占画面 14%；
卧推推出「右下」（实际向上）。

根因：深蹲、俯卧撑、引体这类动作是**「压缩 / 伸展」而非「平移」**，变化区域绕身体中心
对称地扩大收缩，质心天然不动。质心法只适用于整体平移的动作，而那恰恰不是多数力量动作。
要可靠就得有关节/骨骼数据，这批素材没有。

**结论：不画方向线**，改用「高亮脉冲 + 教练生成的发力提示文案」表达发力。

**验收标准**：30 个常见中文动作名的图库命中率 ≥ 90%、错配率 **0**；动图在真机上流畅循环；
肌肉高亮与 manifest 数据一致。

### FR11 Bug 修复：思考内容不展示（本轮的核心 bug）

**现象**：AI 教练对话中，思考区从不出现；同时教练回复实际是一次性蹦出来的，并没有逐字流式。

**根因**（已定位到代码）：

1. `LLMSettings.makeRecordingClient()` 返回的是 `UsageRecordingClient`，而 [UsageRecordingClient.swift](../../AgenticKeepKeep/Core/LLM/UsageRecordingClient.swift) **只实现了 `complete(_:)`，没有实现 `stream(_:)`**。
2. `LLMClient` 协议扩展提供了一个默认 `stream()`：内部调用 `complete(request)`，然后把结果**整体**作为一次 `.text` 事件推送，且**从不产生 `.reasoning` 事件**。
3. 于是生产路径（教练对话走 `makeRecordingClient()`）永远命中这个默认实现：思考内容拿不到，正文也不是增量的。
4. 叠加第二个缺口：非流式响应体 `WireResponse.Message` 也没有解析 `reasoning_content` / `reasoning` 字段，`LLMResponse` 结构里同样没有思考内容字段——所以连降级路径也留不住思考内容。
5. Anthropic 客户端 `complete()` 也只取 `text` / `tool_use` 块，忽略 `thinking` 块。

单测没能拦住，是因为测试用的 `MockLLMClient` 自己实现了 `stream()`，绕开了默认实现。

| 项 | 要求 |
|----|------|
| FR11.1 | `UsageRecordingClient` 实现 `stream(_:)`：**透传**底层事件，仅拦截 `.usage` 事件用于计数，不改变事件序列 |
| FR11.2 | OpenAI 兼容协议非流式响应解析 `reasoning_content` / `reasoning`；`LLMResponse` 增加 `reasoning: String?` |
| FR11.3 | Anthropic 非流式响应解析 `thinking` 块到 `reasoning` |
| FR11.4 | `CoachAgent.reply`（一次性路径）把 reasoning 一并带出，`CoachReply` 增加 `reasoning: String?` |
| FR11.5 | 新增回归测试：用「会流式产出 reasoning 的 mock」包一层 `UsageRecordingClient`，断言 `.reasoning` 事件仍能到达调用方（这正是本次漏掉的用例） |
| FR11.6 | 设置里「显示思考过程」关闭时，思考区不出现也不占位（保持现状语义） |

**验收标准**：单测覆盖「装饰器不吞事件」；真机上 GLM / Kimi 等支持思考的模型能看到思考区逐字增长；不支持思考的模型关闭开关后行为不变。

## 4. 非功能需求

- **性能**：列表滚动 60fps；流式渲染节流后主线程无长任务；记录页 90 天数据下首屏 < 300ms
- **可访问性**：所有图标按钮有 `accessibilityLabel`；支持动态字体（`Dynamic Type`）到 XXL 不截断；支持「减弱动态效果」
- **可测试性**：新增的纯逻辑（流式节流合并、配色映射、摘要格式化）需单测覆盖；视图改动不引入新测试依赖
- **不回归**：现有 139 个单测保持全绿；不改动数据模型与 Agent 的输出契约（UI 层适配）

## 5. 明确不做

- 不做自定义品牌字体、不做换肤 / 主题商店
- 不做 iPad 与横屏专门布局（仍以 iPhone 竖屏为准）
- 不重做引导流程（仅在视觉上对齐新 token）
- 不改数据模型结构、不改 Agent 提示词与 function call 契约
- 不引入第三方 UI 框架（继续纯 SwiftUI）

## 6. 风险

- **视觉改动面大**：涉及 8 个页面的重写，diff 会很大；按批次实现并逐批等 CI 绿，避免一次性大爆炸
- **Emoji 移除后信息密度**：需要确保符号在深色下对比度足够，避免"更干净但更难认"
- **思考区依赖服务商**：思考内容是否返回由模型决定；本轮只保证「返回了就能看到」，不保证所有模型都有
- **浅色模式未在真机验证过**：实现后需在真机分别确认深/浅色下的卡片边界
- **节流可能引入卡顿感**：60ms 窗口需实测，过长会让流式"一跳一跳"
